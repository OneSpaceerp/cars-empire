17. Merchant Mobile App & Unique Coupon Redemption Engine
The Cars Empire merchant experience must include a dedicated mobile application for merchant owners, managers and staff/cashiers. Its highest-priority operational function is secure validation and redemption of customer coupon codes. Each purchased coupon must be an individual, one-time entitlement with a globally unique code and redemption token, even when multiple customers purchase the same deal.
17.1 Business Rules for Coupons
Every purchased coupon instance is unique. If a customer purchases quantity 3, the system creates 3 different coupon records and 3 different redeemable codes.
A deal/offer is a commercial template; a coupon is a unique customer entitlement generated from that template after successful payment.
Coupon codes are globally unique across the entire Cars Empire platform, not merely unique within a merchant or offer.
The QR payload/token is also globally unique and must not be reused, even after expiration or cancellation.
A coupon is single-use unless the offer explicitly supports controlled partial redemption. For standard automotive services, the default is one coupon -> one service redemption.
Redemption must be atomic and concurrency-safe. Two merchant devices must never be able to redeem the same coupon successfully.
Merchant staff can validate a code before redeeming it. Validation is read-only and does not consume the coupon.
Redemption requires an explicit confirmation action by the authorized merchant staff member.
A redeemed coupon creates or links to exactly one primary work order/service entitlement.
Coupons must remain available in the customer app after purchase, including an offline-readable voucher screen. Offline merchant redemption is permitted only where the selected operating policy supports signed offline tokens and later synchronization.
17.2 Coupon Code Generation
Recommended code design: a human-readable code plus a separate opaque QR token. Do not use sequential order numbers, database IDs or predictable timestamps as redeemable secrets.

17.4 Coupon Issuance Flow
The application must never generate usable coupons solely from an add-to-cart event. Coupon generation occurs as part of the authoritative order/payment workflow after successful payment capture or another approved payment state.
Order paid -> determine paid quantity -> generate N unique coupon records -> commit order + coupons transactionally -> publish VoucherIssued events -> notify customer.
If coupon generation fails for any reason, the payment/order workflow must enter a recoverable state and retry idempotently. It must never create duplicate coupons for the same paid order line.

17.7 Merchant Coupon Validation Flow
Merchant staff logs in and is bound to an authorized merchant branch.
Staff scans the customer QR code or enters the unique coupon code.
App sends the token/code plus branch/device context to the validation API.
Server verifies code/token authenticity, status, validity dates, merchant ownership, branch scope, booking requirement, vehicle eligibility and redemption policy.
Server returns a non-destructive VALID or INVALID result with the minimum operational information needed by staff.
Staff reviews the details with the customer and presses CONFIRM REDEMPTION.
Server acquires a row-level lock or equivalent atomic claim on the coupon, re-checks all conditions, creates the redemption, marks the coupon REDEEMED and creates/links the work order in one transaction.
App receives success and displays the redemption/work-order reference.
Customer receives a redemption notification and the service becomes visible in service history.
17.8 Redemption State Machine
Coupon entitlement state:
CREATED -> AVAILABLE -> VALIDATED -> REDEEMING -> REDEEMED -> SERVICE_COMPLETED
Alternative terminal/exception paths:
AVAILABLE -> EXPIRED
AVAILABLE -> CANCELLED
AVAILABLE -> REFUNDED
AVAILABLE -> SUSPENDED
REDEEMED -> REVERSED only through a privileged, reason-coded support/admin process
REDEEMED -> DISPUTED when a merchant/customer case requires investigation; this does not automatically make the coupon reusable
Validation itself must not change AVAILABLE to REDEEMED. The state transition occurs only on the authenticated redemption command.

17.10 Concurrency & Double-Redemption Protection
The redemption endpoint must use a transaction with SELECT ... FOR UPDATE, an atomic compare-and-set, or an equivalent distributed lock strategy.
Before creating the redemption, the service must re-read the coupon and validate that status=AVAILABLE (or the approved pre-redeem state).
Only one redemption may win when two devices submit the same coupon concurrently.
The losing request receives a deterministic ALREADY_REDEEMED response and never creates a second work order.
Idempotency-Key is required for the redeem command. Repeating the same command with the same key returns the original successful response.
A different idempotency key against an already-redeemed coupon must return an entitlement-state error, not another redemption.
17.11 Unique Coupon Generation Pseudocode
Pseudocode:
FOR each paid quantity unit:  LOOP:    random_part = CSPRNG(10-14 characters)    candidate = normalized(prefix + random_part)    IF NOT exists(coupon_code_normalized=candidate):       INSERT coupon with unique constraint       BREAK    ELSE retry  generate independent qr_token with CSPRNGCOMMIT
The database UNIQUE constraint is authoritative. Application-level existence checks are only an optimization and must not be treated as the final collision guarantee.

17.13 Security Requirements for Merchant Redemption
Every merchant device receives a registered device identity and is associated with a merchant/branch scope.
A cashier cannot redeem coupons belonging to another merchant.
Branch scope is checked server-side; the client must not be trusted to select an arbitrary branch.
The app should support PIN/biometric re-entry for fast counter operations without keeping long-lived unrestricted sessions.
Failed code attempts are rate-limited and logged for abuse detection.
After repeated invalid-code attempts, impose progressive throttling and optionally require re-authentication.
Never expose full payment card information, customer phone number or unnecessary personal information to cashiers.
All redemption actions store actor, device, branch, timestamp and reason metadata.
Admin/support reversal of a redeemed coupon must require a reason code and audit trail.
Screenshots or clipboard export of coupon codes should be handled according to the chosen threat model; the server remains the source of truth.
17.14 Merchant App Offline Strategy
Recommended operating mode: online-by-default. Offline redemption is an optional controlled capability, not the default. If enabled, the merchant app receives signed, short-lived validation bundles for the branch. Offline redemption events are stored with monotonic sequence numbers, cryptographic signatures and device identity, then synchronized when connectivity returns. The server reconciles the event and rejects any conflicting or replayed redemption.
17.15 Unique Coupon Lifecycle Example
Example: the customer purchases 3 units of a "Full Synthetic Oil Change" deal.
Order quantity = 3.
Payment captured once for the order.
System generates Coupon A, Coupon B and Coupon C as three separate rows.
Coupon A = CE-OIL-7K4P9Q2M; Coupon B = CE-OIL-4N8X2T6P; Coupon C = CE-OIL-9R3L5W1K.
Each has a unique QR token and independent redemption status.
When Coupon B is redeemed, A and C remain AVAILABLE.
If B is refunded before redemption, B moves to REFUNDED and cannot be redeemed.
If B has already been redeemed, a later refund is handled by the refund/dispute policy and does not silently recreate an AVAILABLE coupon.
17.16 Merchant UX Acceptance Criteria
Merchant staff can reach Scan Coupon within one primary action after login.
QR validation returns a clear result in <= 2 seconds under normal network conditions.
A valid coupon clearly displays the exact service, vehicle and branch context before confirmation.
An invalid or expired coupon clearly explains the operational reason without exposing sensitive system details.
A successful redemption creates exactly one redemption record and exactly one primary work order for the coupon.
Repeated submission of the same redemption request is idempotent.
Two concurrent redemption attempts cannot both succeed.
Each paid quantity generates a separate globally unique coupon code.
Merchant staff cannot change the coupon value, offer, customer, expiry or branch scope from the redemption screen.
Redemption history is searchable by coupon code, order number, date range and work-order reference.

17.18 Implementation Recommendation
Treat the unique coupon service as a dedicated domain module rather than embedding redemption logic inside the merchant UI or general order service. The module owns issuance, uniqueness, validation, redemption, reversal, audit events and synchronization. The merchant app is a thin operational client over this authoritative service. This separation is essential for preventing duplicate redemption, enforcing merchant scope and supporting future channels such as web merchant portal, POS integration, partner APIs and kiosk redemption.
Cars Empire Product Rule: Every purchased service entitlement is a unique coupon. Every unique coupon can be redeemed at most once unless an explicit multi-redemption policy is configured for that offer.
Implementation Clarification: The Merchant App is an operational application for merchant owners/managers/cashiers, and the coupon engine guarantees one unique redeemable coupon code per purchased service unit. A deal does not have one reusable code; every sold unit receives a different code.
